去年 6 月我发过一篇 [消费级基因检测结果自托管平台 Rootara](/posts/Rootara)。当时的架构是标准的前后端分离双容器（Next.js + Python 后端），虽然能跑起来，但实在算不上轻巧——部署动辄要求 2 GB 内存起步，单次导入初始化一份 23andMe 原始数据经常要等上三四分钟，镜像体积也相当感人。

这段时间我把 [Rootara](https://github.com/pzweuj/Rootara) 彻底翻新到了 **v2.0.0**。前端依旧是 Next.js，但在构建阶段直接生成静态文件；后端则完全用 Rust 重写，并且接上了刚完成的 [AdmixRS](/posts/AdmixRS) 和 [HaploGrouperRS](/posts/HaploGrouperRS)。生产镜像里现在已经没有 Python 运行时了，跑成一个单容器，顺带把初始化时间从原来的三四分钟压缩到了 4 秒多。

---

## v2.0.0 到底改了什么

之前耗时长、吃内存，主要问题出在三个地方：Python 运行时底噪高、导入时一次性把大表往内存里拉、祖源和单倍群每次都要重新拉起厚重的脚本环境。v2 把这几块全拆开重写了：

1. **单进程后端 `rootara-server`（Axum / Tokio）**：启动初始化、数据卷迁移、静态资源托管、登录认证、持久化导入队列以及特征公式求值全收进了一个 Rust 进程里。对外只暴露 3000 端口，内部私有 API 监听 `127.0.0.1:8000`，具体的分析 worker 按需拉起、跑完即退。
2. **流式匹配 + 预建索引库**：构建镜像时先通过 `rootara-server build-reference` 把核心注释库编成带索引的 SQLite。导入新样本时，流式读取器 `rootara-reader` 逐行扫过原始基因型，按当前位点即时查库，在一个事务里直接把报告写进数据库，不再全量载入内存映射。
3. **Zstd Parquet 归档（`rootara-archive`）**：新上传的原始文件按小行组保存成 Zstandard 压缩的 Parquet。既能逐字节无损还原原始 TXT 下载，平时前端查看 152 张特征卡片（覆盖 154 个已核验位点）时也只需要读取对应的分型列；遇到缺失位点，系统直接返回 `insufficient_data` 和缺失 RSID，不做任何推断填充。
4. **原生分析引擎替换**：
   - 祖源成分分析换成 [AdmixRS](https://github.com/pzweuj/AdmixRS)（`0.1.0`），跑 K47 模型；
   - Y 染色体（GRCh37）和线粒体单倍群判定换成 [HaploGrouperRS](https://github.com/pzweuj/HaploGrouperRS)（`0.2.0`）。

## 实测对比：体积、内存和导入耗时

拿仓库里的 23andMe 格式模板 `TEMPLATE01.txt`（603,450 行）在 Linux/amd64 Docker Desktop 下做过几轮限制资源对比（统一 2 核 CPU 配额、禁用 swap、空数据卷）。之前旧版跑完一轮往往要 **180 秒** 左右（`v1.0.3` 在 1 GiB 上限下更是跑到了 **269.83 秒**），下面是在 1 GiB 内存上限下的三代对照（完整测试方法见 [import-memory-benchmark.md](https://github.com/pzweuj/Rootara/blob/main/docs/import-memory-benchmark.md)）：

| 指标 | v1.0.3及之前版本 | v2.0.0（首轮 FastAPI） | v2.0.0（全 Rust 后端） |
| --- | ---: | ---: | ---: |
| 镜像体积（磁盘 / 内容） | 2.55 GB / 665 MB | 1.11 GB / 272 MB | **381 MB / 89.8 MB** |
| 导入前静息内存 | 280.4 MiB | 137.3 MiB | **48.9 MiB** |
| 导入并下载后静息内存 | 504.3 MiB | 200.4 MiB | **109.2 MiB** |
| 导入峰值（`memory.peak`） | 983.5 MiB | 286.0 MiB | **140.1 MiB** |
| 从上传到任务完成 | 269.83 秒 | 5.88 秒 | **4.25 秒** |
| 容器 CPU 时间 | 501.85 核秒 | 5.64 核秒 | **3.78 核秒** |

更夸张的是把容器内存上限继续砍到 **512 MiB** 甚至 **256 MiB**，全 Rust 版本依然能顺利完成空卷启动、导入、浏览器下载和全表校验：256 MiB 上限下内核峰值只有 **146.8 MiB**，导入耗时 **4.27 秒**，没有触发 OOM。以前至少要 2 GB 内存的机器才敢跑，现在随便丢进一台低配 VPS 或家用 NAS 里都很宽裕。

结果一致性也核对过：SQLite 全表 328,355 行计算的 SHA-256 三版完全相同，Y 和线粒体单倍群判定一致（`R1b1a1b1a1a2c1a5b1a1` / `L0a'b'f'g`），K47 祖源成分与首轮 v2 完全一致，相比 v1 最大绝对差只有 0.07 个百分点。

## 现在怎么部署

新版合并成了单容器，`compose.yaml` 简单了很多。准备好 Docker 和 Docker Compose 后：

```bash
git clone https://github.com/pzweuj/Rootara.git
cd Rootara
export ADMIN_PASSWORD='请替换为足够长的随机密码'
docker compose up -d
```

或者不拉源码，直接一条 `docker run` 起官方镜像也行：

```bash
docker run -d --name rootara \
  -p 3000:3000 \
  -v rootara_data:/data \
  -e ADMIN_PASSWORD='请替换为足够长的随机密码' \
  ghcr.io/pzweuj/rootara:latest
```

启动后访问 `http://localhost:3000`，默认管理员邮箱是 `admin@rootara.app`（可通过 `ADMIN_EMAIL` 覆盖）。如果是从早期的双容器版本升级，注意新版不支持直接原地迁移旧版目录和环境变量，稳妥起见建议先用全新 `/data` 卷验证跑通，再重新导入原文件；之前留下的老版 TXT 归档，停服后可以执行一次：

```bash
docker compose run --rm --no-deps rootara migrate-archives
```

命令会自动校验 SHA-256 并转成 Parquet，默认保留原文件（加上 `--remove-text` 会在校验通过后删掉旧 TXT）。

## 许可与使用边界

Rootara 主体代码继续沿用 `AGPLv3`，镜像内附带的 AdmixRS 为 `GPL-3.0-only`，HaploGrouperRS `0.2.0` 及随附的 ISOGG 数据限非商业用途（`CC BY-NC-SA 3.0`），对应声明都放在容器内的 `/opt/rootara/licenses/` 下。

另外说明一下，平台内置的特征卡片目前仍属于测试数据阶段，仅作个人探索参考，不能用于任何临床医疗或健康决策。
