## 已知问题：Docker 镜像拉取与 Cloudflare 拦截

在拉取镜像时，有一个已知问题需要提前说明：

当前部署文档中提供的 Docker 命名空间是 **`docker.schema-bio.com`**，底层由 Cloudflare 负责鉴权与反代转发。

如果你在执行 `docker pull` 时遇到了网络超时、连接中断或 403 鉴权失败，**大概率是被 Cloudflare 的防护盾给拦截了**。

目前应对与进展如下：
* **正在排查与分发迁移**：我正在排查和调整 Cloudflare 的防火墙规则，同时已经在着手把全部镜像同步迁移到 **Docker Hub** 和 GitHub Container Registry（**ghcr.io**）进行多渠道分发，后续会提供更通畅的公开拉取通道；
* **临时白名单方案**：如果你现在就等不及想尝鲜拉起服务，可以直接通过邮件把你的公网出口 IP 发送给我，我手动帮你加进 Cloudflare 白名单放行。

## 坦白局：项目与文档仍在高速迭代

虽然“能跑”了，但我必须非常诚实地给大家浇一点冷水、打个预防针。

目前整个项目（包括前端交互、后台服务以及底层的 WDL 调度逻辑）依然处在**密集的收尾与快速迭代阶段**：

1. **文档可能跟不上代码变更**：文档虽然写出了标准部署流程，但很多边缘 case、环境变量默认值或特定发行版下的依赖，难免存在滞后或遗漏。
2. **环境依赖与链路较长**：整套系统涉及前端（YiJian）、核心后端调度（Octopus）、服务层（Sepiida）、miniwdl 流程引擎、本地 Docker 环境以及外部注释数据库的挂载。只要系统环境（Ubuntu 版本、Docker 权限、Python/Node 版本、网络源等）有一点偏差，人工部署就极容易卡在某个细节上。

如果你打算纯靠人工照着文档一步步敲命令，遇到环境不一致时大概率要反复排查报错、抓耳挠腮，非常消耗心力。

## 强烈建议：把部署交给 AI Agent

鉴于上述现实，我强烈建议：**不要人肉硬刚部署，把这件事直接交给 AI Agent 来做。**

在当下的开发范式下，面对多组件、多依赖的开源生信平台，最省心的方式是：
* 打开你常用的终端 Agent 工具（如 Claude Code、Cursor、Windsurf、Codex 或任何具备 Shell 执行与自主纠错能力的 Agent）；
* 把绳墨官网的文档链接 [贻鉴平台部署及使用 | 绳墨生物](https://www.schema-bio.com/docs/yijian) 丢给它；
* 授权它在你的测试机终端里执行命令。

让 Agent 读着文档去拉仓库、配环境、跑服务。一旦中间遇到什么 `pip` 依赖冲突、Node 构建报错、Docker daemon 权限或者端口冲突，Agent 自己就能看报错日志并顺手打补丁搞定，效率比人类手动试错高出几个数量级。

## 极其严肃的声明：严禁用于生产环境！

最后，也是最重要的一点：**当前版本绝对不要上生产！**

请务必注意：
* **仅供测试与科研探索**：现在的开源版本仅作为技术原型展示、内网测试与生信先锋用户的尝鲜评估使用。
* **未经历长期稳定性压测**：系统尚未在极限并发、长期运行与极端边界异常下经历充分的生产级检验。
* **数据安全自负其责**：平台未对生产级灾备和误操作做防呆兜底，在上面跑真实业务或重要样本一旦发生中断、数据损坏或结果偏差，后果完全无法兜底。

一句话：**玩一玩、跑个 Demo、评估一下架构欢迎之至；拿来干正式生产业务，目前还远不到时候。**
